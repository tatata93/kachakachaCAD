# グリッドと視点操作の改善（2026-10-22）

対象は WP-08 の描画・表示操作。基点は `4a23ddbf0`（製品入力は直前の検証済み `2d09964a1` と同じ）。幾何計算、曲線の標本精度、保存形式を変更していない。

## 変更

- 上部のスナップの横に「グリッド表示」を追加。グリッドを隠してもスナップを維持し、作図途中の入力やUndo履歴を変更しない。部品モードで自動的に隠れている場合も、1回押せば表示できる。
- Win95テーマの選択線を紺から明るいオレンジへ変更。暗い縁取りを加え、通常の線より後に描く。役割のある線は中央の役割色を維持し、削除確認は赤を優先する。補助線・基準線の隙間を縁取りで埋めない。
- グリッドを独立した線の一括描画へ変更。画面外の長大な端点をクリップしてから描く。副線の6px基準、色、線幅、アンチエイリアスを維持する。
- 非表示の画像や空の解析データが残っているだけでソフトウェア描画へ切り替わる判定を修正。形状非表示中の解析も不要なラスタライズを要求しない。U/V線や曲率コームなど線だけの解析ではGPUの面描画を維持し、既存の線の重ね描きは残す。解析塗りと可視画像の深度合成は従来どおり保持する。
- 通常線の派生稜線・非表示線は、描画用曲線を組み立てる前に除外する。選択線は全曲線の再走査をせず最後に描く。
- フレーム全体とGPU読み戻し・コピーの時間を別々に計測可能にした。

## 不採用にした案

線だけのビューでGPUフレームバッファを省き、QWidgetへ直接描く案も実装して比較した。しかし細かいグリッドでは95パーセンタイルが約11.6msから約62.8msへ悪化したため取り下げた。GPU QPainterによるグリッド・曲線描画は維持する。失敗した測定は `out/grid-navigation-20261022/after2-*` に保存している。

## 測定方法と限界

同一Windows PC、Release、Qt Windowsプラットフォーム、倍率100%、ウィンドウ2560×1440（比較対象のビューポート1928×1184）、同一モデルで比較。各条件4回のウォームアップ後64回、回転・平行移動を別々に記録。グリッドなし・主線・副線・ほぼ真横の4条件。副線は投影間隔が6px以上となる方向に表示し、真横に近い条件では間引かれる方向もある。

測定対象はカメラ入力から同期QWidget再描画まで。GPUの読み戻し・コピーを含むが、モニターへの実提示FPSや入力機器の遅延そのものではない。60fpsの予算は16.67ms。平均だけでなく中央値、p95、p99、最大、予算超過数をJSONに残す。実モデル原本のSHA-256は前後で一致確認する。

- ユーザー提供の115投影モデル（原本は変更しない）。
- 大規模モデル `samples/series115-heavy/series115-1000-1-80.kcd2`。登録された1,083形状・363,688三角形（保存された表示状態で計測）。
- 空の作図画面。

全条件・全ハードウェアで常時60fpsを保証する結果ではない。GPU読み戻し、可視画像の深度合成、可視解析のCPU処理は残る。これらを隠すためにモデル精度や試験を削減しない。

## 再計測するコマンド

検証済み配布フォルダーのexeを指定する。出力先は実行ごとに分け、他のビルド・GUI試験と重ねない。

```powershell
$env:QT_QPA_PLATFORM = 'windows'
$env:QT_SCALE_FACTOR = '1'
$env:KACHACAD_VIEWPORT_PERF_MODEL = '<読み取り専用で試すkcd2のパス、またはempty>'
$env:KACHACAD_VIEWPORT_PERF_FRAMES = '64'
$env:KACHACAD_VIEWPORT_PERF_OUTPUT = '<新しい出力先>/timings.json'
$env:KACHACAD_SELF_TEST_FILTER = 'HP-GRID-PERF'
& '<検証済み配布フォルダー>/kachakacha_cad_next.exe' --self-test --self-test-report '<新しい出力先>/cases.json'
```

`KACHACAD_VIEWPORT_PERF_EVENTS=1` を加えると、直接カメラを動かす代わりにQtのマウス入力経路（中ボタン移動、Shift＋中ボタン回転）を通る。これはOSからの物理入力の注入ではない。計測後は今回設定した環境変数を解除して通常の全件試験へ混入させない。

`KACHACAD_TRACE_RENDER=1` は、グリッド・形状・線・GPU読み戻し・コピーを標準エラーへ記録する診断用。ログI/Oも時間に加わるため、通常の比較測定とは分ける。

## 検証中に発見して直した点

- 役割付き破線の太い丸端が隙間を埋めた。縁取りのみFlatCapとして周期をそろえ、背景の隙間と線の両方が残ることを画素で確認。
- モードによってグリッドを隠した時にボタンがオンのままとなる点を修正し、1回押せば表示できることを確認。
- 画像の新しいファイルをHTMLにだけ登録したためマニュアル索引検査が失敗した。Markdown本文の画像・撮影名の索引にも登録し、検査成功を確認。
- 新規描画処理の関数長・直接includeの構造検査を修正。試験を緩めず全体検証前に確認した。

既存のCPU描画キャッシュ試験は空の画像プレースホルダーでCPU経路を強制していた。今回その不要な切替を直したため、試験用の専用viewportだけ明示的にソフトウェア描画にする。試験終了時に環境変数を復元し、CPUキャッシュ・画像差替えの確認自体は維持する。

## 残る16.67ms超過と通常起動

直接カメラ更新の計1,536フレーム中14フレーム、Qtマウスイベント経路の計1,536フレーム中9フレームが16.67msを超過した。直接更新ではユーザーモデルのほぼ真横の回転で最大84.05ms、イベント経路では大規模モデルで最大69.95msを記録した。これを除外して常時60fps達成とは扱わない。個々のイベント経路の計測値も同名JSONの `event_rows` に保存した。

診断用の大規模モデル512フレームでは、paintコールバック全体の中央値11.73ms／p95 12.70ms、GPU描画の中央値3.45ms、読み戻し5.48ms、コピー1.42ms。長いフレームでは読み戻しが約12〜14msを占めた。ログI/Oのある別実行なので通常計測の削減率には使わない。これは読み戻しが残るボトルネックの根拠であり、未追跡の84ms／70msの単発超過を同じ原因と断定しない。

今後の60fps改善には、GPU描画結果をCPUへ毎フレーム戻す表示構造の見直しが必要。Qtの画像取得、説明書のシーン描画、画像・解析の深度合成、画面なし試験への影響を検証する必要があり、今回その大規模変更を未検証で配布してはいない。

配布版を通常のWindows GUIで起動し、115投影モデルを読み込んだ。`ready/event_loop/exposed/on_screen/rendered` はすべてtrue。アプリは終了せず使用できる状態にした。証拠は `out/grid-navigation-20261022/desktop-startup.json` と実画面PNG。倍率100%／150%の最終追加7件は、Windows／offscreenの双方で全件成功。初期候補の関連45件／環境と区別して記録している。

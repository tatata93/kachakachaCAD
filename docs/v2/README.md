# kachakachaCAD Wire-first V2 規範文書

## 目的

このディレクトリは、Wire-first V2の完成形を実装前に固定するための唯一の規範である。
実装担当者は製品仕様を発明せず、ここに定義された契約と受入試験を実装する。

V2は、利用者が `面` と `板材` の内部的な違いを意識する現行構造を終了し、
**ワイヤーで形を決め、部品を作り、必要な製作近似と型紙へ進むCAD**へ移行する。

## 規範語

- `必須`: 実装・試験・UIが満たさなければならない。
- `禁止`: 実装してはならない。
- `推奨`: 明確な理由がない限り従う。外す場合はADRが必要。
- `任意`: 実装順序を遅らせられる。勝手に必須へ格上げしない。

英語の仕様・コードコメントでは `MUST`、`MUST NOT`、`SHOULD`、`MAY` を同じ意味で使う。

## 決定済み事項

以下は実装担当者が再検討してはならない。

1. リポジトリを捨ててゼロから作り直さない。検証済みアルゴリズム、テスト、ビルド、配布処理を再利用する。
   ただし規模の実態は次のとおりであり、これを前提に計画する。
   V2は「同一リポジトリ内での全面書き直し + 検証済みアルゴリズムのサルベージ + 旧実装の削除」である。
   新規記述は約77,500行(V1実測66,987行の約1.16倍)、並存ピークは約144,000行・2アプリと見積もる。
   再利用するのはビルド基盤、CI、配布処理、ライセンス監査、Windows 95スキン、
   展開と剛体折りの数学、Gordon曲面の実装、形状ケースである。モデル層とUI層は再利用しない。
2. データモデル、保存形式、UIの操作単位、依存再計算はV2として作り直す。
3. V2完成までは現行アプリを残す。V2の全受入ゲートを通過した切替コミットで旧実装を削除する。
4. 旧 `.kcd` の読込互換は持たない。V2保存形式の一時拡張子は `.kcd2`、正式切替時に `.kcd` とする。
5. 利用者向けの主要オブジェクトは `作図点`、`作業平面`、`ワイヤー`、`形状ガイド`、`部品`、
   `製作モデル`、`型紙`、`グループ` とする。`Surface`、`Plate`、`Body` は利用者向け種類名にしない。
6. 1部品は1つの連結した閉ソリッドである。処理結果が非連結なら複数部品へ分ける。
7. 派生ワイヤーと派生部品は読取専用である。編集したい場合は `現在状態を固定` で独立コピーにする。
8. 押し出しの初回正式範囲は `新規部品`、`足す`、`引く`。交差だけを残す演算は後続とする。
9. 形状ガイドは物理的な面部品ではない。ロフト、投影、近似、断面確認に使う参照形状である。
10. 材料・板厚・積層・紙などの情報は、別の板材オブジェクトではなく部品または製作モデルの属性にする。
11. 内部長さ単位はmm、内部角度はrad、UI角度はdegとする。
12. 名前は重複可能な表示ラベルであり、参照には不変UUIDを使う。

## 要求ID

文書と試験を次の接頭辞で結ぶ。

要求IDの接頭辞は次の4つだけとする。

- `PRD`: 製品原則
- `DOC`: データと依存関係
- `FAB`: 製作近似と型紙
- `UIX`: 画面操作

`WIR` `GEO` `EXT` `MEA` `EXP` `PER` は**要求IDではなくDiagnosticコードの接頭辞**である
(`GEO-W001 DisconnectedChain`、`EXT-005 BooleanWouldBeDisconnected` など)。
要求IDとDiagnosticコードは別の名前空間であり、同じ文字列で両方を指してはならない。
これらの領域の要求は `PRD` 側で拾う。

各必須要件は最低1つの受入試験IDへ対応させる。対応試験がない機能は完成扱いにしない。
各受入試験は、`implementation-work-packages.md` のいずれかのWPの
一次ゲートまたは統合ゲートへ必ず所属させる。所属の無い受入試験を残してはならない。

## 仕様変更手順

1. 不明点をコードで推測しない。
2. 文書同士の矛盾、幾何的な不可能、既存ライブラリ制約を記録する。
3. 既存の決定を変える場合は新しいADRを作る。
4. ADR、規範文書、受入試験を先に変更する。
5. オーナー確認が必要な中核変更だけを質問する。
6. 仕様変更と実装変更を同一コミットへ混ぜない。

## 進捗の正本

実装の状態は `implementation-work-packages.md` の表だけを正本とする。チャットの「完了」、
コミットメッセージ、TODOコメントは進捗の根拠にしない。

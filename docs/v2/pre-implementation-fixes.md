## 1. 着手ブロッカー（WP-02以降の前提）

### B-1. 展開の基準面 ── **オーナー決定済み**

**決定: 展開（型紙・部材近似）の基準面は「利用者が線から作った形状ガイド」とする。**

- 部品（閉ソリッド）は形状ガイドに厚み・材質を与えて作られたものとする。
  その部品を近似・展開するときは、**部品の外皮ではなく、その部品を作った形状ガイドの上で解く。**
- したがって `FabricationModelEntity` は、元Partに加えて
  **`sourceGuideSurfaceId`（その部品の中立面）を必須入力として持つ。** 型を追加すること。
- `PRD-048` の最大偏差・RMS偏差は、**この形状ガイドからの距離**として定義する。
- `ThicknessPlacement`（外側/中央/内側）は、この形状ガイドに対する厚みの付け方を指す。
- **形状ガイドを持たない部品（押し出しだけで作った部品、取り込んだ部品）は近似の対象にできない。**
  その場合は `FAB-N001 NoNeutralSurface`「この部品には展開の基準になる形がありません。
  近似したい面を線から作り直してください」を出して拒否する。**外皮で代用して黙って進めてはならない。**
- 初回切替では**ソリッドからの中立面自動生成（法線方向 -t/2 オフセット）を実装しない。**
  `geometry-contract.md:283` の既存決定と一致する。将来追加候補とする。

理由: V1が実証済みの経路（`Plate = Surface + 厚み`、展開は `Evaluate(u,v,0.5)`）と同じ構造で、
偏差の定義が一意に決まる。板厚を変えても型紙が崩れない。

**この決定に伴い直す文書**

| 文書 | 直す内容 |
| --- | --- |
| `fabrication-contract.md` §5.1 | 入力を「元Partの選択Subshape」から「元Partの形状ガイド + 対象範囲」へ改める |
| `fabrication-contract.md` §3 | `FabricationSettings` に `thicknessPlacement` を明記（現在は §3 の一覧から漏れている） |
| `public-api-contract.md` | `PartFabricationSource` に `sourceGuideSurfaceId` を追加。`GuideFabricationSource` との関係を明記 |
| `architecture-and-data.md` §5 | `FabricationModelEntity` に中立面参照を追加 |
| `kcd2-format.md` §14 | 保存表現に中立面参照を追加 |
| `ui-workflows.md` §10.1 | 「Subshapeを部分選択」を「部品の一部の面だけを近似対象にする」へ。§5に面・辺の選択手段を追加 |
| `acceptance-tests.md` | `AT-FAB-N001`（ガイドの無い部品を近似しようとすると拒否される）を追加 |

### B-2. 面の解析情報が近似アルゴリズムへ渡らない

`fabrication-contract.md` §4 は円筒を「平行母線で厳密展開」、円錐を「扇形として厳密展開」と要求し、
`AT-FAB-001/002` は**解析的な長方形寸法・扇環寸法との一致**を検査する。

ところが `FabricationInputGeometry`（`public-api-contract.md`）が運ぶのは
`SurfaceSample`（uv・点・導関数・法線・主曲率）と `SurfaceBoundary` **だけ**で、
面種別も円筒半径も円錐頂点も面ハンドルも渡らない。**事実上の点群。**

**点群から解析的厳密展開は導けない。** 書かれたAPIのまま実装すると AT-FAB-001/002 は必ず落ちる。

**必須の修正**: `FabricationSurfacePatch` に次を追加する。

```cpp
enum class AnalyticSurfaceKind { Unknown, Planar, Cylindrical, Conical, TangentDevelopable, FreeForm };

struct AnalyticSurfaceInfo {
    AnalyticSurfaceKind kind = AnalyticSurfaceKind::Unknown;
    // Cylindrical: axisPoint, axisDirection, radiusMm
    // Conical:     apexPoint, axisDirection, halfAngleRad
    std::optional<geometry::Vector3> axisPoint;
    std::optional<geometry::Vector3> axisDirection;
    std::optional<double> radiusMm;
    std::optional<geometry::Vector3> apexPoint;
    std::optional<double> halfAngleRad;
    double classificationToleranceMm = 0.0; //!< この判定に使った許容差
};
```

判定は OCCT 側（`BRepAdaptor_Surface::GetType()` と `GeomAbs_SurfaceType`）で行い、
`IFabricationGeometryProvider` が埋める。`Unknown` / `FreeForm` のときだけ標本ベースの
近似展開へ落とす。**「点群だけ渡して厳密展開を要求する」状態を残してはならない。**

### B-5. CIがV2ブランチで一度も動かない

`.github/workflows/windows-build.yml` のトリガは `push: branches: [main]` と `workflow_dispatch` のみ。
V2はmainに触れない方針なので、**WP-01〜WP-11の全期間、CIは自動で1度も回らない。**
それなのに共通DoD第8項は「Windows実機**またはCI**で通る」と書いている。CIは選べない。

さらに `windows-build.yml` のパッケージングは `Copy-Item build/kachakacha_cad.exe` と
**ハードコード**しており、`kachakacha_cad_next.exe` は配布zipに入らない。
つまり **オーナーがV2を触るための実行ファイルが手元へ届く経路が存在しない。**

**WP-01の所有物に `.github/workflows/windows-build.yml` を追加し、着手前に次を済ませる。**

1. `codex/v2-**` ブランチへの push でもトリガする
2. `kachakacha_cad_next.exe` も配布zipへ同梱する（存在する場合のみ、で可）
3. V1ジョブとV2ジョブを分ける（片方の失敗で他方を止めない）

**これ1つで「CIが全期間動かない」と「オーナーがV2を見られない」が同時に解消する。
着手前修正の中で最も費用対効果が高い。**

### D-3. 積層と変厚は専用機能を作らない

**積層**は、製作モデルの設定に **`layerCount`（重ね枚数、既定1）** を1項目足すだけで表す。

- 型紙は枚数ぶん出る（各層に同じ外形、層番号の注記付き）。
- 3Dでは板厚 × 枚数の1枚として表示してよい。層ごとの独立オブジェクトは作らない。
- 厚み方向（外/中/内）は既存の `thicknessPlacement` をそのまま使う。
- **専用の「積層」オブジェクト、専用コマンド、専用の親子関係は作らない。**
  `README.md` 決定済み事項10「積層は部品または製作モデルの属性にする」と一致する。

**変厚**は実装しない。

- V1の変厚（始端厚/終端厚）は **同梱の例題モデル7本すべてで一度も使われていない**（実測）。
- 紙・プラ板は一定厚で購入するもので、削って先細りにする工作はしない。
- 段差が要る場合は積層（層ごとに範囲を変える）で表す。
- 本当に必要になったらオーナーへ確認してから追加する。

### D-4. かごから作るソリッドの面 ── 自動と手動を選べる。形で決め打ちしない

`geometry-contract.md` §7.2/§7.3 を次のように改める。

**大原則: 形の種類で場合分けして「この形には対応しない」と言ってはならない。**
辺の数、曲率、平面性、閉路の入れ子を理由に拒否してよいのは、
**幾何的に成立しない場合だけ**（線が閉じていない、自己交差している、面積が0、
同一直線上に潰れている）。それ以外は、自動が候補を出せなくても
**必ず手動で作れる道を残す。**

#### 手順

線で囲った「かご」から部品を作るとき、閉路ごとに次を行う。

1. **平面判定。** 閉路上の全点が1つの平面へ `modelLinearMm` 内で載るなら、平面で張る。
   **辺の数は問わない**（3辺でも12辺でもよい）。内側に別の閉路があれば穴として扱う。
   平面は一意に決まるので候補提示は不要。黙って張る。
2. **非平面なら候補を作る。** 面が一意に決まらないので、後述の規則で候補を並べ、
   3Dで見せてクリックで選ばせる。
3. **候補がどれも違うなら、その閉路だけ「自分で決める」へ切り替える。**
   断面・ガイド・作り方（ロフト、ガイド付きロフト、網、面をふさぐ）を利用者が指定する。
4. **候補が0個でも失敗にしない。** 3の手動指定へ誘導する。
   「候補を出せませんでした。作り方を指定してください」と出す。
5. 面ごとに独立して 自動採用 / 候補選択 / 手動指定 を持てる。
   1つの部品の中で混在してよい。

#### 候補の作り方（閉路そのものから導く。特定の形に決め打ちしない）

候補は次の4系統から作る。**どれも辺の数に上限を置かない。**

| 系統 | 作り方 | 対象 |
| --- | --- | --- |
| **① 2本の鎖に分けて結ぶ** | 閉路を2点で切って2本の連続した鎖にし、その2本を断面と見なして結ぶ（ルールド／ロフト）。切る位置は、接線の折れが大きい点（接線不連続の大きい順）を優先する。切り方が多いときは折れの大きい上位から最大4通りまで | 辺数を問わない。4辺の箱も、12辺の複雑な縁も同じ規則で扱える |
| **② 境界全体を1枚で張る** | 閉路全体を境界として、膨らみが最小になる面を張る（BoundaryFill） | 辺数を問わない |
| **③ 隣の面の続きとして張る** | 閉路に接する既存の形状ガイドまたは部品の面があれば、その接線方向を引き継いで張る | 隣接面がある場合のみ |
| **④ 内側の線を使って張る** | 閉路の内側を通るワイヤ（利用者が既に描いてある断面線・ガイド線）があれば、それを断面またはガイドとして使う | 内側にワイヤがある場合のみ |

- 各候補に **「元の線からの最大ずれ mm」** を実測して添える。
- 並び順は**ずれの小さい順**。同値なら ①→②→③→④、系統内は切り位置のSegmentIdの昇順とする
  （`DOC-013`/`DOC-014` の決定性を満たすため、乱数と unordered container の反復順を使わない）。
- 候補数は最大8個までとし、超える場合はずれの小さい順に切る。
  **切ったことを画面に出す**（「ほかに N 通りの張り方があります。自分で決めるへ」）。
- **どの系統も作れなかった閉路には、候補0個として手順4へ進む。エラーにしない。**

#### 診断

- `GEO-C001 NonPlanarLoopNeedsChoice`（情報）: 「この囲みは平らでないため、
  張り方が一つに決まりません。候補から選ぶか、自分で決めてください」
- `GEO-C002 LoopNotClosed` / `GEO-C003 LoopSelfIntersects` / `GEO-C004 LoopDegenerate`（エラー）:
  幾何的に成立しない場合だけ。**辺が多い・複雑という理由でエラーにしてはならない。**

#### 受入試験

- `AT-GEO-C001`: 平面だけのかご（6面の箱）が1操作で部品になる。候補提示が出ない。
- `AT-GEO-C002`: 曲面を含むかごで候補が決定的な順に出る。同じ入力で2回実行して同じ順になる。
- `AT-GEO-C003`: **12辺の非平面閉路でも候補が出る**（辺数で拒否しない）。
- `AT-GEO-C004`: 候補0個の閉路で、エラーにならず手動指定へ進める。
- `AT-GEO-C005`: 平面閉路の内側に別の閉路がある場合、穴あきの平面として張られる。

`ui-workflows.md` §9.2 にこの手順を書く。

5. **エラーが日本語で、直し方まで出る。** 英語の例外文が画面に出ない。

落とす判断をする場合は、`product-contract.md` §14(非目標) か §15(切替後の追加候補) へ
**明示的に書き、オーナーの確認を取る。** 黙って消してはならない。

### D-6. 部品番号でまとめる（V1の機能を引き継ぐ）

**製作モデルの入力表は「部品番号」列を持つ。オーナー指示により必須。**

- 対象の面ごとに1始まりの整数を入れる。**同じ番号を付けた面は1つの物理部品としてまとめて近似する。**
- 空欄または0は自動採番とする。自動採番は、連結している面をまとめて同じ番号にし、
  空いている番号を昇順に割り当てる。
- **部材の連続性、折り線の共有、型紙の1枚化は、この部品番号の単位で考える。**
  違う番号の面をまたぐ部材を作ってはならない。
- 番号ごとに、戦略・目標偏差・板厚・材質・重ね枚数を個別に持てる。
  未指定なら製作モデル共通の設定を継承する。
- **型紙は部品番号ごとに出る。**
- 1つの面の近似に失敗しても、他の番号の部品まで巻き添えにしない。
  失敗した番号だけを理由つきで表へ残し、直して押し直せるようにする（V1の挙動を引き継ぐ）。

**これは `fabrication-contract.md` §11 が参照しているのに、どの文書にも定義が無い
`FabricationPartId` の実体である。** 併せて定義すること。

```cpp
struct FabricationPartAssignment {
    FabricationPartId partId;      //!< 1始まり。同じ値＝同じ物理部品
    SubshapeKey        subshape;   //!< または GuideSurfaceRegionId
    FabricationSourceRole role;    //!< Approximate / PreserveShape / ConnectionReference / Ignore
};
```

`kcd2-format.md` §14 の FabricationModel へ、この割り当て表を保存する。

**受入試験** `AT-FAB-P001`: 3枚の面に 部品1／部品1／部品2 を割り当てて近似すると、
部材が部品1側と部品2側に分かれ、部品1の2枚が同じ部材群と折り線を共有し、型紙が2枚出る。

### D-5. Booleanの「足す」が非連結になったとき

**決定: 自動で複数の部品に分ける。実行前プレビューで個数を必ず示す。**

- `PRD-012` / `GEO-S007` を採用し、`geometry-contract.md` §8.4 の「拒否する」を削除する。
- 診断 `EXT-005 BooleanWouldBeDisconnected` は**エラーではなく情報**へ格下げし、
  プレビューに「離れた2つの形になります（部品が2個できます）」と出す。
- **`AT-EXT-009`（足すの結果が非連結になり、2部品へ分かれ、プレビューが2個と示す）を新設する。**
  現状このケースを検証する受入試験が存在しない。

理由: 「離れた位置へ同時に足す」は正当な使い方（左右の手すり、屋根上の別々のベンチレータ）で、
拒否すると作業が止まる。一方、距離不足で届かなかった事故は**プレビューの個数表示で気づける。**

## 2.5. 近似はどの段階で、何を、どう近似するか（実装担当への明示）

実装担当が最も間違えやすい箇所なので、段階・入力・処理を明記する。
`fabrication-contract.md` 冒頭にもこの節を転記すること。

### 2.5.1 全体の流れと、近似が入る位置

```text
[形を決める]
  1. 線を描く                          → Wire
  2. 線から面を作る                    → GuideSurface（形状ガイド。厚みなし）
  3. 面に厚み・材質を与えて部品にする  → Part（閉ソリッド。これが完成品）

[ここから製作。完成品は一切変更しない]
  4. 部品を選び、面ごとに
     「役割」と「部品番号」を割り当てる → FabricationModel の入力
  5. ★近似を実行する★
  6. 部材・折り線・切れ目・開口ができる → FabricationModel（完成品とは別オブジェクト）
  7. 組立スライダー 0〜100% で確認
  8. 出す
     - 型紙（SVG / DXF / 1:1 PDF）
     - 任意の曲げ状態を Part / STL / STEP
     - 任意の曲げ状態を .kcd2（可変のまま or 固定）
```

**近似は 5 でだけ起きる。** 1〜3 の段階では一切近似しない。
6以降で「もう一度近似し直す」こともしない。7と8は5の結果を使うだけである。

### 2.5.2 何を近似するか

**近似の入力は、部品の外皮ではなく「その部品を作った形状ガイド」である**（B-1 / D-1）。

| 対象 | 近似するか |
| --- | --- |
| 役割 `Approximate` を付けた形状ガイドの領域 | **する。これだけが近似の対象** |
| 役割 `PreserveShape`（形を変えずつなぐ） | **しない。** 形はそのまま。近似で動いた分だけ接続を追従させる |
| 役割 `ConnectionReference`（つながりの参照） | **しない。** 位置合わせの基準に使うだけ |
| 役割 `Ignore`（使わない） | **しない。** 読み込みもしない |
| 完成品の Part そのもの | **しない。`FAB-001` により元Partは変更しない** |

形状ガイドを持たない部品（押し出しだけで作った部品、取り込んだ部品）は近似できない。
`FAB-N001 NoNeutralSurface` で拒否する。**外皮で代用して黙って進めてはならない。**

### 2.5.3 どう近似するか（5の中身。この順で行う）

```text
 1. 標本化
    対象の形状ガイド領域を、主曲率・Gauss曲率・曲率勾配・境界・開口・手動線とともに標本化する。
    標本は目標最大偏差から適応細分し、標本化そのものの測定偏差を目標最大偏差の 1/5 以下にする。
    達成できなければ近似計算へ進まず、対象領域と測定偏差を Diagnostic へ出す。
    表示用メッシュを使ってはならない。B-Rep provider から取る。

 2. 領域分け
    平面 / 一方向曲げ / 緩い二重曲率 / 強い二重曲率 に分類する。

 3. 分割候補を作る（優先順位はこの順）
    (1) もとから存在する部品境界
    (2) 利用者が指定した分割線（手動線は自動より優先する）
    (3) 曲率の谷、接線不連続、材料が変わる位置
    (4) 開口のない直線または緩い曲線の位置
    (5) 切れ目で吸収できない強二重曲率
    (6) 最後の手段としての追加パネル
    曲げ母線の向きの候補は、主曲率方向・部品長手方向・手動指定から作る。
    開口を消す候補、またぐという理由だけで微小部材を作る候補は、ここで除外する。

 4. 候補を測って選ぶ
    候補ごとに 9 指標を測る:
      最大偏差 / RMS偏差 / 部材数 / 継ぎ目総長 / 切れ目本数 /
      切れ目総長 / 最小部材幅 / 開口のゆがみ / 組立時の閉じ残り
    選び方は辞書式（重み付き和で精度と部材数を交換してはならない）:
      (1) 必須制約違反を 0 にする
      (2) 目標最大偏差以下にする
      (3) 部材数を少なくする
      (4) 継ぎ目総長を短くする
      (5) 切れ目の本数と総長を少なくする
      (6) 細長すぎる部材を避ける

 5. 各部材の種類を確定する
    平面 / 円筒 / 円錐 / 接線可展 のいずれかにする。
      平面   : 剛体平面変換で展開
      円筒   : 平行母線で厳密展開（解析解。近似で代用しない）
      円錐   : 扇形として厳密展開（解析解）
      接線可展: 母線積分で展開
    Gauss曲率が許容値を超える領域を、そのまま1枚の可展部材として登録してはならない。
    三角形での全面分割は「生成失敗」であり、完成結果として提示してはならない。

 6. 二重曲率の吸収
    残った二重曲率に、境界変更 / 切れ目 / 追加分割 のいずれかを、必要な場所にだけ入れる。
    切れ目の形は、対象曲面の計量と目標の曲げ量から決める。固定半径で決め打ちしない。

 7. 開口を部材へ切り分ける
    開口が部材境界をまたぐ場合、またぐ全ての部材へ取り分を作る。
    切り口は必ず細かく割ってから面へ写す（曲面の上で弦になって窓が崩れるため）。
    片が面から外れても取り分ごと捨てない（窓そのものが消えるため）。
    丸い窓を多角形へ置換してはならない。開口を消して成功扱いにしてはならない。
    ※ V1 の `ClipClosedLoopIntoBands` と `SnapPointOntoSurface` が、この3点への実証済みの回答。

 8. 部品番号ごとにまとめる
    同じ部品番号の面から出た部材を1つの物理部品としてまとめる（D-6）。
    違う番号をまたぐ部材を作ってはならない。

 9. つながりを追従させる
    役割 `PreserveShape` / `ConnectionReference` の面と、周辺のワイヤを、
    近似で動いた分だけ追従させる。対応付けは名前や最近点で行わず、
    面上の UV または意味的 SubshapeKey を正本にした Attachment として保存する（§12）。
    最近点は初回の候補探しにだけ使う。対応先が消えたら赤表示し、勝手に近い部材へ移さない。

10. 実測して見せる
    最大偏差と RMS 偏差を mm で表示する。見た目だけで再現度を評価させない。
    目標偏差を部材数上限内で達成できない場合は、超過を警告し、勝手に上限を超えない。
```

### 2.5.4 近似の結果として持つもの

```text
FabricationModel
  部品番号ごとに
    部材（種類、展開形、3D形、最大/RMS偏差）
    折り線（つながったまま折る線）
    切れ目（途中まで切る線。形と深さ)
    開口（部材ごとの取り分。またいだ場合は接合点IDで対応付ける）
    対応辺（別部材と接着する辺の組）
  組立状態（全体 0〜100% と、折り線ごとの個別角度）
  Attachment（周辺の追従情報）
```

**すべての組立状態で、部材境界・折り線・切れ目・開口を、
曲線種類を保ったまま 3D ワイヤーとして取り出せること**（`FAB-007`）。
ワイヤーと部品を同時に固定するとき、**部品の境界と出力ワイヤーは別々に計算しない**（`FAB-008`）。
V1 の `PartFoldState.cpp` は、境界ワイヤーを先に作ってそこから面を張ることで
これを構造的に達成している。同じ作りにすること。

### 2.5.5 近似の再実行

- 元の形状ガイドが変わったら、5 を丸ごとやり直す。部分更新しない。
- やり直せない場合は直前の結果を `古い結果` と表示し、元Partも直前結果も壊さない（`FAB-006`）。
- 手動で付けた役割・部品番号・手動境界は、元Wireへの参照として保存されているので、
  やり直しでも失われない。投影不能になった手動線を最寄りへ無言移動してはならない。

## 6. 「完了」の定義（現状は崩れている）

### 6-1. 「下位試験」の定義

共通DoD第2項「対応する受入試験**またはそのWPで実行可能な下位試験**がある」の
「下位試験」に定義が無く、**担当AIの自己申告で完了にできる抜け穴**になっている。
`README.md`「チャットの完了を進捗の根拠にしない」がこの1行で無効化されている。

**定義: 下位試験とは、次をすべて満たすものをいう。**

1. そのWPが所有するファイルだけをビルドして実行できる。
2. 期待値が**数値または固定Diagnosticコード**で書かれている（目視・画像一致だけでは不可）。
3. 対応する受入試験IDを、試験のコメントに明記している。
4. `implementation-work-packages.md` の該当WP行に、試験名と「なぜ本番の受入試験を
   このWPでは実行できないか」を1行で記録している。

**この4条件を満たさないものを下位試験と呼んではならない。**

### 6-2. ゲートの循環

依存表は非循環だが、**ゲートに指定された試験の前提をたどると循環する。**

| WP | ゲート試験が実際に要求するWP | 循環 |
| --- | --- | --- |
| WP-03 | `AT-DOC-001` が保存再読込 → WP-05 / `AT-DOC-004` が有効Part → WP-07 | WP-03 → WP-05 → WP-03 |
| WP-05 | `AT-EXP-001` が全Entity kind・全Feature type → WP-06/07/09 | WP-05 → WP-09 → WP-07 → WP-06 → WP-03 → WP-05 |
| WP-09 | `AT-FAB-006/011` が保存再読込 → WP-05（**依存表にWP-05が無い**） | 未宣言 |
| WP-08 | `AT-UIX-011` が全53コマンド → WP-07/09/10/11 | WP-08 → WP-11 → WP-09 → WP-07 |

**対応:**

1. **WP-09の依存にWP-05を追加する。**
2. **各WPのゲートを2段に分ける。**
   - `一次ゲート`: そのWPの所有ファイルだけで判定できる試験。**WPの完了条件はこれだけ。**
   - `統合ゲート`: 他WPが揃ってから判定する試験。**WP番号を明記して統合担当が持つ。**
3. **`AT-UIX-011`（全コマンドregistryの完全性）はWP-08から外し、WP-12へ移す。**
   53コマンドが揃うまで判定できないため。

## 7. 規模と体制（申告を実態に合わせる）

### 7-1. 「作り直しではない」は成立しない

`README.md` 決定済み事項1「リポジトリを捨ててゼロから作り直さない。検証済みアルゴリズム、
テスト、ビルド、配布処理を再利用する」──**この文自体は真**（CI・パッケージング・
ライセンス監査・CMake環境検出は再利用される）。しかし規模の申告が実態と違う。

| | 行数 |
| --- | ---: |
| V1 実測（src 59,486 + tests 7,501） | **66,987** |
| V2 新規見積り（WP別に積算、中央値） | **約77,500**（レンジ 62,700〜91,900） |
| 比 | **約1.16倍** |
| 並存ピーク時のリポジトリ | 約144,000行・2アプリ・約100テストターゲット |

- `DOC-004` が「旧 `Project` をV2の正本として再利用してはならない」と明示 → `Project.cpp/.h` 5,783行は捨てる
- UI層 36,972行は全面書き直し
- 「既存処理を再利用する場合はV2値型へ移植し」→ 移植は行としては新規

**`README.md` へ次の一文を追加する:**

> V2は「同一リポジトリ内での全面書き直し + 検証済みアルゴリズムのサルベージ + 旧実装の削除」である。
> 新規記述は約77,500行（V1の約1.16倍）、並存ピークは約144,000行と見積もる。
> ビルド基盤、CI、配布処理、ライセンス監査、Windows 95スキン、展開・折りの数学、
> Gordon曲面の実装、形状ケースは再利用する。モデル層とUI層は再利用しない。

**書き直すという判断自体は妥当。** 名前参照18フィールド、`tool_ ==` 比較143箇所、
常にfalseを返すスタブ、`MainWindow.cpp` 7,590行という構造負債は実在する。直すのは申告だけ。

### 7-2. 並列度は実質1

- 受入試験83本のうち **クラウド（Qt・OCCT無し）で回せるのは26本（31%）**。
  fake providerを作り込んでも最大37本（45%）。**残り46〜57本はWindows必須。**
- WP-06以降はほぼ全部Windows: GEO/EXT 19本＝クラウド0本、UIX 11本＝0本、EXP＝0本。
- **ビルドディレクトリが1つ。** `CMakePresets.json` の binaryDir は固定。
  3並列は同一ninjaディレクトリの奪い合いになる。CMakeCache破損、`.ninja_log` 競合、
  リンク中のPDB衝突が起きる。18.3「競合予防」7項目は全部ソース競合の話で、
  ビルド競合を1件もカバーしていない。
- 統合担当自身もmerge後検証で同じPCを使う。

**対応:**

1. **担当ごとにビルドディレクトリを分ける。** `CMakePresets.json` へ
   `windows-msvc-v2-a` / `-b` / `-c`（binaryDir `build-v2-a` 等）を足し、
   統合担当が割当時に指定する。
2. **git worktree を使う。** `git worktree add ../kachakachaCAD-wp05 codex/v2-wp05` のように
   担当ごとに作業ツリーを分ける。同一ツリーで複数担当が作業しない。
3. **同時に走らせるのは最大2担当まで**とし、片方はクラウドで回せるWP（WP-02/03/04/05）に限る。
4. **B-5 のCI整備を先に済ませる。** これが済めばWindows検証をCIへ逃がせる。

### 7-3. オーナー確認点を3つにする

現状の人間確認点は「WP-12完了後、WP-13の直前」の**1つだけ**。
最も不確実なWP-09（製作近似、新規8,500行、V1でADR 15本と展開方式4系統を消費した領域）を
**中間確認なしで通る。** 完成しなければ成果ゼロ、途中で仕様が変われば全損。

**確認点を3つにする。各時点でCIが `kachakacha_cad_next.exe` 入り配布zipを出すこと（B-5）。**

| 時点 | 確認してもらう内容 |
| --- | --- |
| **WP-07完了時** | 線を描く → 押し出す → 部品ができる → 足す/引く が動く。オーナーが実際に触れる |
| **WP-09完了時** | 曲面を部材へ近似して**型紙が出る**。ER1/ER2で偏差を見る |
| **WP-12完了時** | 全機能。従来の切替確認 |

### 7-4. 実現可能性スパイクを前倒しする

**`AT-FAB-013`（ER1/ER2 1/87 の9条件同時充足）を、WP-09の完了条件ではなく
WP-06/WP-07の直後の「実現可能性スパイク」として先に通す。**

D-1（形状ガイドを中立面とする）が実際に成立するかを、8割消化してから確かめるのは最悪。
スパイクの範囲は「ER1のノーズ1箇所を形状ガイドから近似し、型紙を出し、
最大偏差とRMSを実測する」まで。UIも保存も要らない。

### 7-5. テストフレームワーク移行の所有者を決める

`acceptance-tests.md` は「1件失敗で残りを停止しない」を要求している。
しかしV1の自己診断は `return fail(...)` の**fail-fast一本道**で、最初の1件で残り4,000行が走らない。
`docs/refactoring-plan.md` 項目6（テストフレームワーク移行）は**未着手のまま所有WPが無い。**

**WP-01の所有物に追加する。** 10〜30分かけて回すゲートが1件目で止まると、
1サイクルで得られる情報が1件だけになり、7-2 のサイクルタイム問題が致命化する。
仕様書に「**V1のfail-fast一本道を移植してはならない**」と明記すること。

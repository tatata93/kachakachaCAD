## 2. 統合ブランチと作業ツリー

1. ownerが指定しない場合はmainから `codex/wire-first-v2-integration` を作ります。
2. mainへ直接実装commitをpushしません。
3. 統合ブランチのHEADを各担当の `BASE_COMMIT` として伝えます。
4. 依存WPをmergeしたら、未着手担当へ新しいBASE_COMMITを伝えます。
5. 古いbaseの担当成果はそのままmergeせず、最新integrationへrebaseまたはmergeして再検証させます。
6. **担当ごとに git worktree を分けます。**
   ```
   git worktree add ..\kachakachaCAD-wp05 codex/v2-wp05
   ```
   複数担当を同じ作業ツリーで作業させないこと。`WORKTREE_PATH` として担当へ伝えます。
7. **担当ごとにビルドディレクトリを分けます。** `CMakePresets.json` へ
   `windows-msvc-v2-a` / `-b` / `-c`（binaryDir `build-v2-a` 等）を用意し、
   `BUILD_PRESET` として担当へ伝えます。
   **これをしないと、並行担当が同一ninjaディレクトリを書き合ってCMakeCacheが壊れます。**

## 3. 割当規則

- 依存が全て完了したWPだけを割り当てます。
- 1担当は同時に1WPだけです。
- 1WPを複数担当へ重複割当しません。
- `WP-03` のdomain公開型、`WP-04` のgeometry公開型、root CMake、進捗表には各時点で所有者を1人だけ置きます。
- 並行化は所有ファイルが重ならず、public APIが凍結済みで、
  **worktreeとビルドpresetが分かれている場合だけ**許します。
- UI担当をcore契約より先行させません。
- **同時に走らせるのは最大2担当までとし、うち少なくとも1つはクラウドで検証できるWP
  （WP-02 / 03 / 04 / 05）にします。**
  受入試験83本のうちクラウドで回せるのは26本（31%）だけで、WP-06以降はほぼ全部Windows必須です。
  Windows必須WPを2つ同時に走らせると、1台のPCの奪い合いになって並列の利得がありません。
- **割当前に、その担当が一次ゲートを実行できるかを確認します。**
  クラウド担当でWindows必須の一次ゲートを持つWPは、代行実行の手段を先に決めてから渡します。

担当へは `docs/v2/agent-master-prompt.md` の `ASSIGNED_WORK_PACKAGE`、`INTEGRATION_BRANCH`、
`BASE_COMMIT`、`WORKTREE_PATH`、`BUILD_PRESET`、`TARGET_PLATFORM` を埋めた全文を渡します。
要約だけを渡してはなりません。

## 5. ゲートの2段構成

**依存表は非循環ですが、ゲートに指定された試験の前提をたどると循環します。**
例: WP-03のゲート `AT-DOC-001` は保存再読込を要求 → WP-05必須 → WP-05はWP-03に依存。

各WPのゲートを次の2段に分け、**進捗表へ明記してください。**

- **一次ゲート**: そのWPの所有ファイルだけで判定できる試験。**WPの完了条件はこれだけ。**
- **統合ゲート**: 他WPが揃ってから判定する試験。**WP番号を明記して統合担当が持つ。**

あわせて次を修正します。

1. **WP-09の依存にWP-05を追加**（`AT-FAB-006/011` が保存再読込を要求するのに依存表に無い）。
2. **`AT-UIX-011`（全53コマンドのregistry完全性）をWP-08から外し、WP-12の統合ゲートへ移す。**
   53コマンドが揃うまで判定できません。
3. **どのWPにも所属していない受入試験12本を割り当てる**（`pre-implementation-fixes.md` 第6-3節）。
   特に **`AT-WPL-001`〜`003`（作業平面の全11方式）** と
   **`AT-ARC-001`〜`005`（coreのQt/OCCT非依存＝V2の中核主張を検証する唯一の試験）** が
   無所属でした。必ず割り当ててください。

## 6. 担当成果の受入

担当AIの報告を受けたら、自己申告を信じて即mergeせず次を確認します。

1. 進行中ロックcommitが先にpushされている。
2. branch baseが指定commitを含む。
3. 変更がWP所有範囲内である。
4. 契約IDと試験IDが報告されている。
5. success/invalid/cancel/retry試験がある。
6. test skip、許容差拡大、固定値stub、UIだけの実装がない。
7. **下位試験で代替した項目が、`agent-master-prompt.md` G-1 の4条件を満たしている。**
   「動作を確認した」「手で試した」は下位試験ではありません。
   条件を満たさない代替が1つでもあれば差し戻します。
8. public header変更が規範APIと一致する。
9. 名前参照、Qt/OCCT型漏れ、絶対path、unordered順依存がない。
10. Windows/CIが必要な一次ゲートは結果がある。
11. branchがpush済みで、進捗表の完了commitが最後にある。
12. **仕様変更commitと実装commitが分かれている。**

不足が1つでもあればmergeせず、具体的なfile、契約ID、失敗testを付けて同じ担当へ戻します。

## 7. 実現可能性スパイク（WP-07直後、必須）

**`AT-FAB-013`（ER1/ER2 1/87 の総合条件）を、WP-09の完了条件としてではなく、
WP-07完了直後の「実現可能性スパイク」として先に通してください。**

- 範囲: ER1のノーズ**1箇所だけ**を、形状ガイドから部材へ近似し、型紙を出し、
  **最大偏差とRMS偏差を実測する。** UIも保存も要らない。捨てて構わないコードでよい。
- 目的: B-1の決定（形状ガイドを中立面とする）が実際に成立するかを確かめる。
- **これが通らないならV2全体の前提が崩れます。** 8割消化してから発覚するのが最悪の結果です。
- 結果（実測値つき）をオーナーへ報告してから WP-08 以降へ進みます。

WP-09は製作近似の新規約8,500行で、V1ではこの領域だけでADRを15本消費し、
展開方式を4系統作って3系統削除しています。最も不確実な領域を中間確認なしで通してはいけません。

## 9. 仕様の不明点

- private実装詳細は、契約を満たす最小の方法を統合担当が決め、必要なら短いADRへ記録します。
- 既に規範に決定がある事項をownerへ聞き直しません。
  **`pre-implementation-fixes.md` 第2節（オーナー決定事項）は決定済みです。聞き直さないこと。**
- 数学的に不可能、ライセンスに抵触、中核思想を変える必要がある場合だけ、案と影響を揃えてownerへ質問します。
- 回答待ちでも、独立したready WPは進めて構いません。

## 10. オーナー確認点（1回。ただし条件つき）

**オーナー指示 2026-09-08: 「私がテストする際には実用できるクオリティのソフトが
完成している必要がある」。したがって、中間確認のために未完成の実行ファイルを渡しません。**

確認は **WP-12完了後の1回だけ**です。そのとき渡すものは、
`pre-implementation-fixes.md` D-8 の7条件を**すべて**満たしていること。

| 時点 | 見てもらう内容 | 前提 |
| --- | --- | --- |
| **WP-12完了時** | 全機能。線を描くところから型紙とSTL/STEP/PDFまで通しで使える | D-8 の7条件を全部満たしている。配布zip、全画面画像、切替チェックリスト |

### 中間確認を挟まないぶんの埋め合わせ（必須）

確認点を減らすと、方向の間違いが見つかるのが遅くなります。次で埋めます。

1. **実現可能性スパイク（§7）は必ず行う。** WP-07直後にER1/ER2の型紙が出るかを確かめる。
   **オーナーへは渡さず、統合担当が自分で見る。** ここが通らなければ設計をやり直す。
2. **1WPごとにWindows実機で全試験を通す。** 通っていないものを完了にしない。
3. **画面が絡むWPは、必ず実機のスクリーンショットで目視する。**
4. **V1（main）は生かしておく。** V2が長引く間、オーナーが実際に使えるのはV1だけです。
   V1の修正をV2の存在を理由に止めない。

## 11. mainと配布

- WP-12完了前にV2をmainの正式アプリへ切り替えません。
- WP-12は全試験、ER1/ER2 1/87 fixture、画像マニュアル、配布zip実起動まで行います。
- **オーナー確認点3の後にだけ WP-13 を開始します。**
- WP-13は旧コード削除と正式名切替だけを行い、新機能を混ぜません。
- WP-13後に `.kcd2` を正式 `.kcd` へ切り替え、同一内容のZIP+JSONであることを再検査します。
- mainへmergeする前にWindows full check、self-test、配布zipからの実起動、sample open、30% STEP、
  1:1 PDFを通します。

### V1側の扱い

**V2が長期戦になる間も、V1はオーナーが日々使う唯一の出荷物です。**

- V1の修正・改善をmainへ入れることを妨げないでください。V2の存在を理由に止めない。
- ただしV1へ**新しい大機能を足さない**でください。WP-13で削除する物を増やすだけです。
- 統合ブランチは定期的にmainからmergeし、V1の修正を取り込みます。
- **着手時点でmainに入っていないV1の完成済み作業がある場合は、先にmainへ入れてください。**
  未マージのまま放置すると、V2が失敗したときに何も残りません。

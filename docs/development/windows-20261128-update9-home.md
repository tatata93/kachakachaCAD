## 通常アプリ経路の初回読込比較

更新9は、64形状以上かつ4論理CPU以上の場合に、文書の書出しをnative形状・表示メッシュの転送準備と重ねる。
自宅の4論理CPUで `samples/series115-heavy/series115-1000-1-80.kcd2` の作業コピーを使用した。
部品1,083と形状ガイド2の計1,085形状。原本とコピーのSHA256は
`8e08619769ef38028af3c2a9f4a6699e607c1e7e8066f3301100aa149b72b4d5`。

同じ更新9の同梱EXEで `HP-OPEN-OWNER actual KCD load timing` だけを完全一致で選択した。
`KACHACAD_OWNER_OPEN_FILE` を作業コピーにし、`KACHACAD_OPEN_ARCHIVE_SERIAL=1` と同変数を外した既定を交互に各3回実行した。
全体を直列化する `KACHACAD_OPEN_SERIAL` は使用していない。画面側の並列復元は両条件で有効のままとした。
アプリ本体の `--self-test` から通常の `OpenDocumentFile` を通した。各ケースは内部の `CacheScope` で空の一時キャッシュを作り、初回と再読込を続けて行った。
Windowsプラットフォームを指定し、開発用PATH・Qt変数は除外した。OSファイルキャッシュは消去せず、並行したシステム診断も行っていない。

初回転送準備は、cache missの作業プロセスで `ready-to-write-transfer.elapsed_ms - rebuild-and-adopt.elapsed_ms` として測った。
文書書出しからnative形状・表示メッシュの取得・書出し完了待ちまでを含め、並列化前に行う文書書出しを測定から落とさない。
初回読込全体はアプリ本体の `open/complete.elapsed_ms`。EXE起動時間と後続の描画は含めない。

全6ケース・計12読込が成功し、各回の1,085形状、初回・再読込の文書定義一致、cache miss/hit、原本・コピー・EXEの不変を確認した。
